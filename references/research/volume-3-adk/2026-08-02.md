# Volume 3 research log — 2 August 2026

## Question

Which current ADK and Agent Platform contracts can a forward-deployed engineer
safely build against, and which production controls remain application/customer
responsibilities?

## Baseline checked

- `google-adk` v2.6.1, release commit `740582e9f283cd23ff5cec1389400b422513f765`.
- ADK docs commit `308c7831800d4543ac230f5a64da335796575135`.
- ADK samples commit `739bb34c0bd22516dbbda88f3e5a9f9375bb963c`.
- `google-cloud-aiplatform` v1.163.0 available from the Python package index;
  current Agent Runtime docs require at least 1.144 for bring-your-own-container.

## Source conclusions

1. `google.adk` publicly exports `Context`, `Event`, and `Workflow`; graph helpers
   publicly export `JoinNode`, `RetryConfig`, `START`, and `node`.
2. `Event` carries `output` and `node_info`; route/state convenience values are
   transformed into event actions.
3. Function nodes pass through `RequestInput`; dynamic nodes use
   `await ctx.run_node(...)`; a parent handling interruption must be resumable.
4. v2.6.1 source supports task-mode workflow agents. The imported chapter's
   older statement that task mode is disabled is no longer current.
5. Graph workflows do not currently support live streaming. A `JoinNode` waits
   for every predecessor and can become stuck if a branch emits no output.
6. `RequestInput` supplies interrupt ID, payload, message and response schema.
   It does not itself establish customer identity, authorization or segregation.
7. Agent Runtime currently supports object, source, Dockerfile, container-image
   and Developer Connect deployment routes; Python is the supported language.
8. `AdkApp` connects deployed ADK agents to Agent Platform Sessions. Customer
   business transactions, approvals and idempotency still require explicit
   systems of record and control-owner decisions.
9. ADK evaluation supports test/evalset data, exact/in-order/any-order tool
   trajectories, response match and model-judged groundedness/safety/quality.
   Some criteria use paid Vertex AI evaluation services and require cloud auth.

## Resulting implementation decisions

- Keep a graph workflow for auditable topology and a separate deterministic
  application service for policy, approval binding and writes.
- Demonstrate `RequestInput` only as a non-authoritative UX interrupt.
- Require canonical action digest, authenticated approver, group authorization,
  expiry and requester/approver separation before high-risk execution.
- Require a durable production tool gateway; ship only an in-memory test double.
- Treat uncertain writes as reconciliation work, not retryable failure.
- Run hermetic safety invariants on every change and run model/online criteria in
  an approved customer project with a reviewed dataset and budget.
- Keep deployment guarded and dry-run by default; production qualification stays
  Draft until sandbox, recovery, load, security and independent review evidence exists.
